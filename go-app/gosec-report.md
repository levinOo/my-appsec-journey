## 🚨 2. Детальный разбор критических уязвимостей (High Severity)

### 2.1. Hardcoded Credentials (CWE-798)
* **Файл:** `config/config.go:4`
* **Описание:** В коде обнаружен захардкоженный токен доступа AWS API. Хранение секретов в исходном коде может привести к их утечке через системы контроля версий.
* **Рекомендация:** Удалить секрет из кода. Использовать переменные окружения (`os.Getenv`) или специализированные хранилища секретов (HashiCorp Vault, AWS Secrets Manager).

### 2.2. Command Injection (CWE-78)
* **Файл:** `internal/handlers/system.go:15`
* **Описание:** Обнаружено выполнение системной команды (`os/exec.Command`) с передачей несанитизированного пользовательского ввода в аргументы. Это позволяет атакующему выполнить произвольный код на сервере (RCE).
* **Рекомендация:** Отказаться от вызова системной утилиты `ping`. Использовать нативные Go-библиотеки для работы с ICMP-запросами (например, `golang.org/x/net/icmp`).

### 2.3. Path Traversal (CWE-22)
* **Файл:** `internal/handlers/system.go:30`
* **Описание:** Чтение файла через `os.ReadFile` осуществляется по пути, который полностью контролируется пользователем. Это позволяет прочитать любые системные файлы сервера (например, `/etc/passwd`).
* **Рекомендация:** Использовать `filepath.Clean` и жестко привязать (chroot) чтение файлов только к определенной безопасной директории (использовать `os.Root` для Go >= 1.24).

## ⚠️ 3. Проблемы средней критичности (Medium Severity)

### 3.1. SQL Injection (CWE-89)
* **Файл:** `internal/handlers/user.go:14`
* **Описание:** Формирование SQL-запроса происходит путем конкатенации строк (`fmt.Sprintf`). Хотя Gosec пометил это как Medium, в контексте веб-приложения **это критическая уязвимость**.
* **Рекомендация:** Использовать параметризованные запросы (prepared statements), передавая переменные через `?` или именные параметры драйвера БД.

### 3.2. Отсутствие таймаутов сервера (CWE-676)
* **Файл:** `cmd/server/main.go:26`
* **Описание:** Использование стандартной функции `http.ListenAndServe` без настройки таймаутов делает сервер уязвимым к атакам типа Slowloris (исчерпание пула соединений).
* **Рекомендация:** Создать кастомный экземпляр `http.Server` и явно задать параметры `ReadTimeout`, `WriteTimeout` и `IdleTimeout`.

---

## 🛠 4. План действий (Remediation Plan)

1. Завести задачи в таск-трекер на исправление уязвимостей уровня High и SQLi.
2. Внедрить сканер `gosec` в CI/CD pipeline (GitLab CI / GitHub Actions), настроив падение пайплайна при обнаружении уязвимостей уровня High.
3. Провести аудит всех сторонних зависимостей (SCA) перед релизом.
